# Хакатон: AI-driven интерфейс управления рекламными кампаниями (MVP)

> Задание: MVP-скоуп AI-driven интерфейса управления рекламными кампаниями
> Мок-данные и контракты — в [`mock-data.md`](mock-data.md) и `mocks/`

---

<a id="sec-1"></a>
## 1. Контекст и цель

**Сервис управления рекламными кампаниями** — менеджер создаёт кампанию, задаёт аудиторию (сегменты), места показа, креативы (баннер + контент-экран), проходит модерацию и публикует кампанию в Content Broker (CBRO), который доставляет её во фронтальные приложения (например, СберБанк Онлайн).

**Сегодня** это ручной многошаговый процесс через классический UI: список кампаний → карточка с десятками форм → модерация → публикация. Кроме кампании, есть множество вспомогательных сущностей, большинство которых в рамках MVP отсутствуют. Порог входа высокий, создание кампании занимает много времени и требует знания многих тонкостей процесса.

**Цель хакатона** — прототип **AI-driven интерфейса** (диалоговый ассистент): по текстовому брифу менеджера AI собирает кампанию целиком — параметры, аудиторию, места показа, креативы, — валидирует, показывает результат и отправляет на модерацию через API бэкенда. Примерный формат бэкенда предоставлен в настоящем задании.

**Что ожидается от решения:**
1. Диалоговый интерфейс (чат): пользователь формулирует бриф, AI структурирует его в доменную модель и доводит до готовности к запуску.
2. Агент с инструментами (function/tool calling) поверх API кампаний и справочников: кампании, сегменты, места показа, типы баннеров запрашиваются инструментами.
3. Human-in-the-loop: AI показывает собранную структуру (превью кампании) и запрашивает подтверждение перед любым редактирующим действием.
4. Валидация: JSON баннеров/контента должен проходить схемы ([§2.6](#sec-2-6)–[§2.7](#sec-2-7)); ошибки и warnings бэкенда превращаются в понятные сообщения и цикл исправления.
5. Демо end-to-end: бриф → кампания с 1–2 креативами → превью → отправка на модерацию → статус.

## 2. Доменная модель (MVP)
### Предоставляется в качестве ориентира, если будет желание структурировать данные иначе, это допустимо. Эта модель - сильно упрощенная (порядка 10% объема полей и справочников плюс структурные правки в сторону более простых интерфейсов) версия реальной.

<a id="sec-2-1"></a>
### 2.1 Карта связей

```text
CAMPAIGN ──1:N── BANNER   (один JSON-контент)
         ├─1:N── CONTENT  (один JSON-контент, тип PROMO)
         ├─1:N── CREATIVE (banner + content? + channel)
         ├─N:M── PLACE    (места показа)
         ├─[ ]── сегменты включения (плоский список кодов)
         ├─[ ]── сегменты исключения (плоский список кодов)
         └─ N ── теги (справочник)

Справочники: SEGMENT(+SEGMENT_TYPE), PLACE, BANNER_TYPE, CHANNEL, TAG, TOPIC
Интеграции (заглушки): CBRO-экспорт при активации
```

<a id="sec-2-2"></a>
### 2.2 Кампания (`CAMPAIGN`)

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | long | авто | Идентификатор |
| `name` | string(100) | да | Название, уникальное, непустое |
| `marketingName` | string(100) | нет | Маркетинговое название |
| `startDate` / `startTime` | date / "HH:mm" | да | Начало показа |
| `endDate` / `endTime` | date / "HH:mm" | нет | Конец показа (если задан — позже начала) |
| `topic` | enum | да | Тематика: фиксированный enum, 11 значений (см. `mocks/topics.json`); создание новых значений не предусмотрено |
| `tags` | [id] | нет | Теги из справочника TAG |
| `keywords` | string(512), ';' | нет | Ключевые слова |
| `audienceType` | enum | да | `ALL_USERS` \| `SEGMENTED` ([§2.4](#sec-2-4)) |
| `weight` | double | да (дефолт 0) | Вес кампании для ранжирования в местах показа |
| `initialCtr` | double | да (дефолт 15) | Начальный CTR до накопления статистики |
| `state` | enum | авто | `DRAFT`/`ON_MODERATION`/`NEEDS_WORK`/`APPROVED`/`ACTIVE`/`ACTIVE_EDITING`/`STOPPED`/`ARCHIVED` ([§2.3](#sec-2-3)) |
| `published` | boolean | авто | Показ активен: кампания выгружена в CBRO. `true` ставит только `activate`, `false` — только `stop`; не является состоянием жизненного цикла ([§2.3](#sec-2-3)) |
| `author` / `lastEditAuthor` | string | авто | Аудит |

В телах POST/PUT словарные поля (`topic`, `tags`, `places`) передаются объектами `{value, label}` (label — как в справочнике); в ответах GET возвращаются сырые значения (string / [id]).

<a id="sec-2-3"></a>
### 2.3 Жизненный цикл

`state` — позиция кампании в конвейере «сборка → модерация → публикация». Флаг `published` — признак того, что показ фактически идёт (кампания выгружена в Content Broker). Это не вторая машина состояний: у флага ровно два писателя — `activate` (true) и `stop` (false).

```text
основной поток: DRAFT → ON_MODERATION → APPROVED → ACTIVE → STOPPED
возвраты:       ON_MODERATION → NEEDS_WORK (decline) → ON_MODERATION (to-moderation повторно)
                APPROVED → DRAFT (правка снимает одобрение)
правка живой:   ACTIVE → ACTIVE_EDITING → ON_MODERATION → APPROVED → ACTIVE (повторная активация)
вне скоупа:     ARCHIVED — объявлен в enum, не используется (§6.4)
```

| Состояние | Значение |
|---|---|
| `DRAFT` | Черновик, редактируется, на модерацию не отправлялась (или одобрение снято правкой) |
| `ON_MODERATION` | Отправлена на модерацию, ожидает решения |
| `NEEDS_WORK` | Отклонена модератором, требует правок |
| `APPROVED` | Одобрена модератором, готова к активации |
| `ACTIVE` | Активна, одобренная версия доставляется клиентам |
| `ACTIVE_EDITING` | Активная кампания редактируется — внесённые правки ещё не опубликованы |
| `STOPPED` | Показ остановлен вручную |
| `ARCHIVED` | Объявлено в enum, в MVP не используется ([§6.4](#sec-6-4)) |

**Правило показа.** `published=true` означает, что клиенты видят кампанию, независимо от `state`. Уход живой кампании на модерацию (`ACTIVE_EDITING → ON_MODERATION → APPROVED`) показ **не останавливает**; внесённые правки становятся видимы только после повторного действия `activate`. Единственная точка остановки показа — `stop`.

| Переход | API | Условия | Результат |
|---|---|---|---|
| Создание | `POST /campaigns` | — | `state=DRAFT`, `published=false` |
| Обновление шапки/мест | `PUT /campaigns/{id}` | state ∈ {DRAFT, NEEDS_WORK, APPROVED, ACTIVE, ACTIVE_EDITING} | `DRAFT`/`NEEDS_WORK`: state не меняется; `APPROVED` → `DRAFT` (одобрение снимается); `ACTIVE`/`ACTIVE_EDITING` → `ACTIVE_EDITING` |
| Правка дочерних сущностей | `PUT/DELETE` баннеры, контент, креативы; `PUT /segments` | те же состояния, что и у `PUT /campaigns/{id}` | — |
| На модерацию | `POST /{id}/to-moderation` | state ∈ {DRAFT, NEEDS_WORK, ACTIVE_EDITING}, **валидация без ошибок** ([§4](#sec-4)) | `state=ON_MODERATION` |
| Отклонить | `POST /{id}/decline` | state=ON_MODERATION, тело: `{"comment": "..."}` (обязателен) | `state=NEEDS_WORK`; комментарий сохраняется в журнале аудита |
| Одобрить | `POST /{id}/approve` | state=ON_MODERATION | `state=APPROVED` |
| Активировать | `POST /{id}/activate` | state=APPROVED; вызов заглушки CBRO ([§5](#sec-5)) | `state=ACTIVE`, `published=true` |
| Остановить | `POST /{id}/stop` | published=true | `state=STOPPED`, `published=false` |
| Удалить | `DELETE /{id}` | state ∈ {DRAFT, NEEDS_WORK} и published=false | — |

Правка в `APPROVED` снимает одобрение и возвращает кампанию в `DRAFT` — изменённую версию обязан снова одобрить модератор. Удалять можно только то, что никогда не публиковалось: живая кампания (`published=true`), оказавшаяся в `DRAFT`/`NEEDS_WORK`, не удаляется — сначала `stop`.

`STOPPED` — замороженное состояние: кампания остаётся в списке и в журнале аудита, но не редактируется (`UPDATE_NOT_ALLOWED`) и не возобновляется. В MVP из неё переходов нет: resume/archive — вне скоупа ([§6.4](#sec-6-4)).

Нарушение предусловий перехода — HTTP 400 с кодами `UPDATE_NOT_ALLOWED`, `TO_MODERATION_NOT_ALLOWED`, `DECLINE_NOT_ALLOWED`, `APPROVE_NOT_ALLOWED`, `ACTIVATE_NOT_ALLOWED`, `STOP_NOT_ALLOWED`, `DELETE_NOT_ALLOWED` ([§4](#sec-4)). Действия `decline`/`approve` доступны только роли `campaignModerator`, остальные пишущие операции — `campaignManager` (роль передаётся в заголовке `X-Role`, [§3](#sec-3)); нарушение — `ROLE_FORBIDDEN`. При одновременном нарушении роли и состояния возвращается `ROLE_FORBIDDEN` (проверка роли первее).

<a id="sec-2-4"></a>
### 2.4 Аудитория

Два типа аудитории:
- **`ALL_USERS`** — все пользователи; сегменты не задаются.
- **`SEGMENTED`** — требуется ≥ 1 сегмент включения.

Сегменты — **плоские списки кодов**:
- **включение**: коды объединяются по OR («попадает любой из сегментов»);
- **исключение**: коды вычитаются из включения.

Сохраняются одним вызовом: `PUT /campaigns/{id}/segments` с телом `{"included": ["CITY_MSK"], "excluded": ["EXC_UNSUBSCRIBED"]}`. Для кампаний с `audienceType=ALL_USERS` сегменты не задаются: вызов с непустыми списками возвращает ошибку `SEGMENTS_FORBIDDEN_FOR_ALL_USERS` ([§4](#sec-4)). Инвариант действует на уровне кампании: смена `audienceType` на `ALL_USERS` через `PUT /campaigns/{id}` при непустых сохранённых сегментах возвращает ту же ошибку — сначала очистите сегменты (`PUT /segments` с пустыми списками), затем меняйте тип аудитории.

Справочник сегментов приходит из внешней системы (Ads Profile API) — в MVP это статичный словарь `mocks/segments.json`: код, название, тип, состояние (`ACTIVE`/`NEW`), количество клиентов. Выбирать можно только сегменты в состоянии `ACTIVE` (у `NEW` счётчик 0 — AI должен это объяснить).

<a id="sec-2-5"></a>
### 2.5 Места показа (PLACE)

Место показа — слот во фронтальном приложении (например, «промо-блок на главном экране»):

| Поле | Описание |
|---|---|
| `id`, `code` | Идентификатор и уникальный код (`mainScreenStories`) |
| `description` | Человекочитаемое название |
| `defaultBanner` | Код типа баннера по умолчанию (`STORY` / `SMART_BANNER`) — подсказка AI, какой креатив генерировать |
| `state` | `ACTIVE` \| `INACTIVE` (в неактивное место кампанию выбирать можно, но появится warning) |

Связь кампания↔места: список placeId внутри создания/обновления кампании; в телах POST/PUT — в словарной обёртке `{value, label}`, где label — это `code` места (так во всех примерах `mocks/campaign_create_payloads.json`): `places: [{"value": 2, "label": "mainScreenSmartBanner"}]`; в ответах GET возвращаются сырые id: `"places": [2]` ([§2.2](#sec-2-2)).

Создание места показа: `POST /places` — обязательны `code` и `description`; `id` генерирует бэкенд, `state` всегда `ACTIVE`. `defaultBanner` у созданных мест не задаётся — правило `PLACE_NO_CREATIVE` для них не применяется ([§7.2](mock-data.md#sec-7-2) mock-data). Теги: `POST /tags` — обязательно только `name`, `id` генерирует бэкенд ([§10.4](#sec-10-4)).

<a id="sec-2-6"></a>
### 2.6 Баннеры

**Баннер** = креатив-превью кампании: у баннера один JSON-контент.

`POST /campaigns/{id}/banners` — тело:

```json
{
  "name": "Смарт-баннер осенний",
  "bannerTypeId": 2,
  "content": { ...JSON ниже... }
}
```

**JSON-контент баннера** (единая схема для обоих типов):

| Поле | Тип | Обяз. | Ограничения |
|---|---|---|---|
| `title` | string | нет | ≤ `titleMaxLength` типа баннера (STORY 100, SMART_BANNER 250) |
| `text` | string | нет | ≤ `textMaxLength` типа (STORY 500, SMART_BANNER 1000) |
| `titleStyle`, `textStyle` | object | нет | `{fontSize: 10..40, fontWeight: thin\|light\|regular\|medium\|semi-bold\|bold, textColor: "#RRGGBBAA"}` |
| `background` | object | нет | `{"color": "#RRGGBBAA"}` |
| `image` | object | нет | `{"url": "https://..."}` — произвольная https-ссылка на изображение |
| `buttonName` | string | нет | Название кнопки |
| `actionType` | enum | да | `default` \| `externalLink` \| `openSmartLink` \| `closeCampaign` \| `doneCampaign` |
| `link` | object | нет | `{"iOS": "...", "android": "...", "web": "..."}` — deep-link/URL; обязателен при `externalLink`/`openSmartLink`, **запрещён** при `closeCampaign`/`doneCampaign` |
| `voiceOver` | string(200) | нет | Озвучка для accessibility |

Минимальный валидный JSON: `{"actionType": "default"}`.

Ключи `iOS`/`android`/`web` внутри `link` независимы: достаточно заполнить нужные платформы (в моках встречаются частичные наборы — баннер 202 без `web`, кнопка контента 309 только с `web`). Валидация соответствия ключа `link` каналу креатива в MVP отсутствует (кода в каталоге ошибок нет).

<a id="sec-2-7"></a>
### 2.7 Контент (документы)

**Контент** = экран, открывающийся при нажатии на баннер. В MVP — единственный тип **`PROMO`** (промо-экран из вертикального стека компонентов).

`POST /campaigns/{id}/contents` — тело:

```json
{
  "name": "Промо-экран: премиальная карта",
  "contentType": "PROMO",
  "content": { ...JSON ниже... }
}
```

**JSON-контент PROMO:**

```text
{role: "promo", component: linearContainer}
linearContainer = {role: "linearContainer", axis: "v", aligns?: string (напр. "lt"), style?: {backgroundColor}, components: [1..6]}
components — только 3 роли:
  text   = {role: "text", format: "none"|"html" (обязателен), text, textStyle?}
  image  = {role: "image", url (обязателен), aspectRatio?}
  button = {role: "button", text, actionType, link?, textStyle?, style?}   // правила link — как у баннера
```

Валидации: `axis` всегда `"v"`; `format` обязателен у text; `url` обязателен у image; `actionType` — из enum баннера ([§2.6](#sec-2-6)); рендерер расставляет компоненты сверху вниз автоматически.

Не валидируется в MVP (кодов нет в каталоге `mocks/validation_rules.json`): подмножество HTML для `format: "html"` (в моках — только `<b>`), допустимые значения `aligns` (в моках — `"lt"`), диапазоны `textStyle`/`style` компонентов и `aspectRatio`. Ограничения стилей [§2.6](#sec-2-6) на компоненты контента формально не распространяются — используйте их как рекомендацию для генерации.

<a id="sec-2-8"></a>
### 2.8 Креативы

**Креатив** связывает баннер + контент + канал:

```json
POST /campaigns/{id}/creatives
{
  "name": "Креатив Android",
  "bannerId": 201,
  "contentId": 301,          // необязательно: креатив без контента валиден
  "channelCode": "ANDROID"
}
```

- Уникальность: (campaign, bannerId, channelCode) — два креатива на одну пару запрещены.
- Совместимость каналов: у типа баннера есть список допустимых каналов (`mocks/banner_types.json`): STORY — [iOS, ANDROID]; SMART_BANNER — [iOS, ANDROID, WEB]. Креатив STORY в WEB — ошибка валидации.
- Коды каналов регистрозависимы и пишутся точно как в `mocks/channels.json`: `iOS`, `ANDROID`, `WEB`.

<a id="sec-3"></a>
## 3. API (полная поверхность MVP: 7 GET-справочников + POST /places и /tags + 22 операции с кампаниями и дочерними сущностями)

Пагинация/фильтры в MVP не нужны — данных мало; списки возвращаются целиком.

```text
Справочники (GET, без параметров):
  /topics       /tags          /channels      /banner-types
  /segment-types  /segments    /places

Создание записей справочников модуля кампаний:
  POST   /places                     — {code, description}; id — авто, state=ACTIVE
  POST   /tags                       — {name}; id — авто

Кампании:
  GET    /campaigns                  — список, лёгкий CampaignListItemDto (id, name, state, published, topic, даты)
  GET    /campaigns/{id}             — кампания + баннеры + контент + креативы + сегменты + места (CampaignDetailsDto, ниже)
  POST   /campaigns                  — создать (шапка + places), CampaignInfoDto (§2.1 mock-data)
  PUT    /campaigns/{id}             — обновить шапку/места
  DELETE /campaigns/{id}             — удалить (DRAFT/NEEDS_WORK без активного показа)
  PUT    /campaigns/{id}/segments    — {"included": [...], "excluded": [...]}; запрещено при audienceType=ALL_USERS
  POST   /campaigns/{id}/banners     — создать баннер
  PUT/DELETE /campaigns/{id}/banners/{bannerId}
  POST   /campaigns/{id}/contents    — создать контент
  PUT/DELETE /campaigns/{id}/contents/{contentId}
  POST   /campaigns/{id}/creatives   — создать креатив
  PUT/DELETE /campaigns/{id}/creatives/{creativeId}
  GET    /campaigns/{id}/warnings    — прогон валидации: {errors: [...], warnings: [...]}
  GET    /campaigns/{id}/audit       — журнал аудита кампании (формат записи — §3 «Аудит»)
  POST   /campaigns/{id}/to-moderation | /decline | /approve | /activate | /stop
```

**Форма `GET /campaigns/{id}` (CampaignDetailsDto).** Шапка возвращается сырыми значениями ([§2.2](#sec-2-2): `topic` — string, `tags`/`places` — [id]); дочерние сущности — вложенными коллекциями `banners[]`, `contents[]`, `creatives[]` и объектом `segments: {included, excluded}`. Структура элементов коллекций — как записи `mocks/campaign_banners.json`, `campaign_contents.json`, `campaign_creatives.json`, `campaign_segments.json`.

**Семантика PUT.** Все PUT-операции (`PUT /campaigns/{id}`, дочерние `PUT`, `PUT /segments`) — полная замена представления объекта; частичная правка выполняется как `GET` → изменение → `PUT` полного объекта.

Для сценария «предложить и создать» ([§10.4](#sec-10-4)) POST-эндпоинты создания записей предусмотрены для справочников, ведущихся в модуле кампаний (places, tags); темы — фиксированный enum; внешние (сегменты) и системные (типы баннеров, каналы) справочники — только чтение.

Ошибки API — HTTP 400 с телом `{"errors": [{"code": "...", "message": "...", "field": "..."}]}` — коды из `mocks/validation_rules.json`. Ссылки на несуществующие сущности (id кампании/баннера/контента/креатива, `bannerTypeId`, `placeId`, id тега, `channelCode`) — HTTP 404 с тем же телом и кодом `ENTITY_NOT_FOUND`.

**Пользователь и роли.** Каждый запрос содержит заголовки `X-User` (логин) и `X-Role` (`campaignManager` | `campaignModerator`); бэкенд проставляет `author`/`lastEditAuthor`/`actor` по `X-User` и возвращает оба заголовка в ответе.

**Аудит.** Все пишущие действия (создание/обновление сущностей, переходы жизненного цикла) бэкенд записывает в отдельную таблицу аудита: какая сущность, какие правки, когда, кем. Чтение — `GET /campaigns/{id}/audit` (все записи по кампании). Формат записи журнала:

```json
{
  "entity": "CAMPAIGN|BANNER|CONTENT|CREATIVE|SEGMENTS",
  "entityId": 201,
  "action": "CREATE|UPDATE|DELETE|TO_MODERATION|DECLINE|APPROVE|ACTIVATE|STOP",
  "changes": {"title": {"from": "…", "to": "…"}},
  "at": "2026-10-22T16:45:00",
  "actor": "petrova.m",
  "comment": null
}
```

`changes` — diff изменённых полей `{поле: {from, to}}`; `null` для CREATE и переходов ЖЦ. Мок `mocks/lifecycle_transitions.json` — проекция этого журнала (только переходы ЖЦ кампании, `entity=CAMPAIGN`).

<a id="sec-4"></a>
## 4. Валидации и warnings

**Errors** (блокируют `to-moderation`) — полный каталог с кодами и сообщениями: `mocks/validation_rules.json`. Основные группы:
- шапка: имя/даты (end позже start, формат `HH:mm` — и `startTime`, и `endTime`), topic, длина полей; `NAME_DUPLICATE` не срабатывает при сохранении кампании с её собственным текущим именем;
- аудитория: `SEGMENTED` без включений; несуществующий/не-ACTIVE сегмент; сегменты при `ALL_USERS` (`SEGMENTS_FORBIDDEN_FOR_ALL_USERS`);
- баннер: JSON-схема, лимиты title/text по типу, `actionType`↔`link` (обязателен/запрещён);
- контент: JSON-схема, `format` у text, `url` у image, вложенность PROMO;
- креатив: канал не разрешён типу баннера, дубликат (campaign+banner+channel);
- места: не задано ни одного места показа;
- жизненный цикл и роли: переход из недопустимого state (`*_NOT_ALLOWED`), редактирование кампании в `ON_MODERATION`/`STOPPED` (`UPDATE_NOT_ALLOWED`), действие недоступно роли (`ROLE_FORBIDDEN` — возвращается первым, если нарушены и роль, и состояние).

**Warnings** (не блокируют, показываются до модерации):
1. «Не для всех мест показа настроены креативы»
2. «Некоторые места показа деактивированы»
3. «У кампании отсутствуют теги»

**Требование к AI:** сообщения валидации конвертировать в человекопонятные объяснения + предложение исправления («Заголовок 132 символа, лимит для STORY — 100. Сократить до …?»).

<a id="sec-6"></a>
## 6. Требования к AI-интерфейсу

<a id="sec-6-1"></a>
### 6.1 Пользовательские сценарии (MVP)

1. **Создание кампании по брифу.** («Кампания по премиальной карте для клиентов 26–45 в Москве, смарт-баннер на главном, до конца года») → AI заполняет `name`, `marketingName`, даты, `topic`, теги, подбирает места показа по описанию, предлагает сегменты из справочника (с count клиентов). Неоднозначно (даты, сегменты) — уточняющий вопрос, а не догадка.
2. **Аудитория.** Подбор сегментов включения/исключения с объяснением (тип, количество клиентов, активен/нет); определение `ALL_USERS` vs `SEGMENTED`.
3. **Креативы.** Генерация баннера (title/text/стили/кнопка/ссылка — валидный JSON) + контента PROMO + креатива (канал по месту показа). Медиа произвольные (генерация картинок — см. [§6.4](#sec-6-4)). Если в брифе просят сторис — STORY-баннер + PROMO-контент.
4. **Правила показа.** Вес и начальный CTR по тексту («максимально широкий охват» → предложить weight).
5. **Проверка и публикация.** Прогон валидаций/warnings, человекочитаемая сводка, исправление по команде, отправка на модерацию, объяснение статуса (включая `NEEDS_WORK` — комментарий модератора из журнала аудита).
6. **Обслуживание (lite).** Стоп кампании; показать, что собрано; объяснить, почему нельзя активировать.

<a id="sec-6-2"></a>
### 6.2 Архитектурные требования

- **Агент + tools**: инструмент на каждый вызов API [§3](#sec-3) с JSON-схемой параметров; справочники — только через инструменты.
- **Строгая валидация генерации**: JSON баннера/контента валидируется по схемам [§2.6](#sec-2-6)–[§2.7](#sec-2-7) **до** отправки в API; enum — только из словарей.
- **Human-in-the-loop**: любое редактирующее действие — после явного подтверждения; перед отправкой — превью собранной кампании.
- **Устойчивость к ошибкам API**: 400 с errors ([§3](#sec-3)) → диалог с предложением исправлений (демо-кейс: заведомо невалидный JSON баннера или превышенный лимит title на черновике 101/108; кампания 104 из моков — кейс цикла исправлений после decline, warnings, а не 400).
- **Пошаговость**: кампания собирается итерациями, состояние черновика сохраняется между сообщениями.

<a id="sec-6-3"></a>
### 6.3 Обязательные требования к прототипу

- Чат + создание черновика кампании (`POST /campaigns`).
- Подбор сегментов и мест показа из справочников.
- Генерация баннера, контента, креатива в кампании с предпросмотром (как эта сущность будет выглядеть у клиента, отрисовка произвольная).
- Валидация + отправка на модерацию.
- Серверный аудит: все пишущие операции и переходы ЖЦ записываются бэкендом в отдельную таблицу (сущность, какие правки, когда, кем — мок `mocks/lifecycle_transitions.json`); ассистент показывает историю пользователю через `GET /campaigns/{id}/audit`
- Демо на моках (`mocks/`) — бэкенд можно воспроизвести по этому описанию и файлам моков.

<a id="sec-6-4"></a>
### 6.4 Возможные дополнительные функции прототипа (будут преимуществом, но четкие алгоритмы реализации не предлагаем)

- Версии сущностей и А/Б-эксперименты.

<a id="sec-10"></a>
## 10. FAQ

<a id="sec-10-1"></a>
### 10.1. Как менеджер заводит кампанию сейчас и где теряется больше всего времени и ошибок?

Текущий процесс: создании основной кампании с обязательными полями → заполнение карточки кампании с несколькими вкладками (инфо, аудитория, места показа, креативы, правила показа) → отправка на модерацию. Каждый шаг — отдельная форма с десятками полей; только часть данных можно менять независимо, порядок шагов не фиксирован, но сильно зависит от заполненных и незаполненных полей (например, нельзя отправить на модерацию недособранную кампанию).

Где теряется время: (1) заполнение основной информации и экономики кампании; (2) подбор разных вспомогательных параметров, в MVP это только сегменты и места показа — справочники большие, у многих сущностей есть свои особенности, которые надо учитывать; (3) креативы — самый трудоёмкий блок: JSON баннера и контента собирается в редакторе по сложным и часто неочевидным правилам; (4) цикл модерации: после отклонения нужно, чтобы другой сотрудник нашел время проверить правки (это требует большого внимания к деталям) и одобрить их. С учетом того, что кампании заводятся десятками, задержки на каждом этапе могут сильно осложнить процесс.

Где чаще всего ошибки: JSON креативов (ручаня настройка требует очень много времени), недозаполненность (забытые обязательные поля при разных типах аудитории и других настройках), несоответствие креативов местам показа, даты.

Что сокращает AI, а что остаётся человеку: AI забирает перенос данных из брифа в поля, подбор сегментов/мест по описанию, генерацию валидного JSON креативов и объяснение ошибок модератора. Человеку остаются решения о фактическом наполнении кампании, ее особенностях и подтверждение результата работы агента — см. [§10.2](#sec-10-2).

<a id="sec-10-2"></a>
### 10.2. Какой результат ожидается от ассистента: черновик, заявка на согласование или кампания, готовая к публикации?

Результат MVP-сценария — **кампания в статусе `ON_MODERATION`** (заявка на согласование): черновик создан и полностью собран, валидации пройдены. Термины разделены так:

- **«готовность к запуску»** = state `APPROVED`: кампания собрана и одобрена модератором, но ещё не активна;
- **«фактический запуск»** = `published=true` (переход в `ACTIVE` через `activate`): единственная точка публикации, из которой кампания уходит в Content Broker.

Права подтверждения: отправить на модерацию и вносить правки — менеджер (владелец черновика); одобрить/отклонить — модератор (отдельная роль; в реальной системе модератор не может одобрять свои же правки — «правило двух рук»); активировать — менеджер, но только после approve. Модерация может выполняться внутри ассистента, но только под ролью `campaignModerator` (заголовок `X-Role`, [§3](#sec-3)) и строго по явному подтверждению человека ([§6.2](#sec-6-2)). Активная кампания остаётся редактируемой (правки переводят её в state `ACTIVE_EDITING`).

Может ли AI запускать? Да, при выполнении обоих условий: (1) модератор одобрил (approve — всегда человек), (2) пользователь явно подтвердил действие ассистента (human-in-the-loop, [§6.2](#sec-6-2)). Без одобрения модератора AI активировать не может ни при каком подтверждении. Нескольких согласующих в MVP нет: одна роль модератора. Важный нюанс для MVP: бэкенд-заглушка `activate` всегда возвращает успех (ошибки экспорта в MVP не эмулируются), поэтому «запуск по подтверждению» реализуем внутри MVP-скоупа.

<a id="sec-10-3"></a>
### 10.3. Какие поля кампании обязательны, а какие могут иметь значения по умолчанию?

Основные данные о кампании — таблица в [§2.2](#sec-2-2); обязательность дочерних сущностей — [§2.4](#sec-2-4)–[§2.8](#sec-2-8); дефолты (`weight=0`, `initialCtr=15`) применяются бэкендом. Сводно:

| Блок | Обязательно | Опционально / дефолт |
|---|---|---|
| Инфо | name, startDate+startTime, topic, audienceType | marketingName, endDate/endTime (пусто = бессрочно), tags, keywords |
| Аудитория | для SEGMENTED — ≥1 включённый сегмент | для ALL_USERS — ничего |
| Показ | места показа (≥1) | weight (0), initialCtr (15) |
| Креативы | у баннера — bannerTypeId, actionType; на уровне кампании отсутствие баннеров/креативов **не** блокирует модерацию — даёт только warning PLACE_NO_CREATIVE (кампания 104 дошла до ON_MODERATION без баннеров) | контент (креатив без него валиден), text/title, стили, кнопка, ссылка (зависит от actionType), voiceOver |

Примеры для сверки результата: кампания 101 — все необязательные поля заполнены, кампания 103 — только обязательные («минимальный» эталон); тела создания — `mocks/campaign_create_payloads.json`; каталог ошибок валидации — `mocks/validation_rules.json`.

<a id="sec-10-4"></a>
### 10.4. Что означает «предложить создать» отсутствующую сущность и какие сущности менеджер вправе создавать?

Менеджер создаёт кампанию и её дочерние сущности (баннеры, контент, креативы, состав мест показа, списки сегментов). Для справочников правило такое: если справочник ведётся в том же модуле кампаний (места показа, теги), ассистент вправе предложить создать отсутствующую запись; темы — фиксированный enum, записи не создаются; внешние и системные справочники — только выбор из существующего.

- **Ведутся в модуле кампаний** (места показа, теги): если в справочнике нет записи, соответствующей брифу, ассистент сам предлагает создать новую — показывает форму с полями сущности, предварительно заполненными из брифа. Пользователь проверяет и заполняет поля; после подтверждения запись создаётся (`POST` в справочник) и **сразу привязывается к кампании** — без отдельного прохода в настройки справочника. Контракты: `POST /places` — обязательны `code` и `description` (id генерирует бэкенд, `state` всегда `ACTIVE`; `defaultBanner` не задаётся — правило `PLACE_NO_CREATIVE` для таких мест не применяется); `POST /tags` — обязательно только `name` (id генерирует бэкенд).
- **Внешние и системные** (сегменты — приходят из Ads Profile API; типы баннеров, каналы): создание не поддерживается. Ассистент подбирает ближайшую по смыслу существующую запись или сообщает, что подходящей нет. Данные не фантазировать: id/коды существующих записей — только из словарей.

Механика диалога: сначала предложение (имя записи, значения полей, к какой кампании будет привязана), затем явное подтверждение пользователя ([§6.2](#sec-6-2)), затем создание и привязка одним шагом.

Для MVP команды реализуют заглушку бэкенда сами и добавляют POST-эндпоинты создания записей для справочников первого типа (допустимое расширение поверхности [§3](#sec-3)). Аппрув новой записи администратором/Data-инженерами в MVP не моделируется — созданная запись сразу доступна и привязана.

<a id="sec-10-5"></a>
### 10.5. Где находятся актуальные справочники и какие данные доступны команде на хакатоне?

Актуальные справочники и исторические кампании доступны только в виде **синтетического датасета**, подготовленного по структуре реальной системы: `mocks/` (18 JSON-файлов, все enum валидны, кампании покрывают все состояния жизненного цикла) + описания в `mock-data.md`. Дамп продакшн-БД и доступ к реальным клиентским данным не предоставляются.

Сегменты — **готовые предрассчитанные списки**: у каждого кода фиксированный count клиентов; конструктор условий (возраст × город × продукты × траты по MCC) и пересчёт аудитории в скоуп не входят — из брифа выбираются готовые коды. Медиа для креативов — произвольные (генерация изображений — см. [§6.4](#sec-6-4)).

<a id="sec-10-6"></a>
### 10.6. Как устроены условия начала и окончания показа?

В MVP показ управляется **только расписанием по датам**: `startDate+startTime` (обязательно), `endDate+endTime` (необязательно — бессрочный показ), end > start. Это единственный механизм выхода/входа кампании: нет ни объёмных лимитов (показы/клики), ни событийных триггеров в реальном времени.

Часовой пояс в MVP не задаётся (используйте UTC). Частотных ограничений и исключений из аудитории нет, кроме явного списка сегментов-исключений ([§2.4](#sec-2-4)): исключённый клиент не видит кампанию независимо от других условий.

Конфликты правил в MVP не возникают по построению: у кампании один период и один набор условий. Ошибка валидации `DATE_RANGE_INVALID` — единственный случай «конфликта» (end ≤ start), разрешается на этапе сохранения, до модерации. 

<a id="sec-10-7"></a>
### 10.7. Как разрешаются коллизии и приоритеты между кампаниями?

В MVP эти моменты не моделируется.

При конфликте (несколько активных кампаний претендуют на один экран одного клиента) в реальной системе работает механизм ранжирования: у каждого места показа задан лимит выборки, и кандидаты сортируются по весу кампании и CTR — чем выше `weight`, тем выше шанс показа. В MVP этот механизм **не реализуется** — он существует на стороне фронтальных систем, а не в API кампаний. `weight` — просто число в паспорте кампании; ассистент может его подобрать по брифу («широкий охват» → выше вес) и обязан объяснить пользователю, что итоговый выбор кампании для показа выполняет система показов, а не сервис кампаний.

Приоритеты задаёт менеджер через `weight` при создании/редактировании; специального конфликта-резолвера и проверок пересечения кампаний в MVP нет — две кампании могут свободно висеть на одном месте показа.

<a id="sec-10-8"></a>
### 10.8. Какие ограничения ИБ и регулятора на использование AI-моделей?

Для MVP используйте любые модели, доступные команде (внешние облачные API разрешены, если есть доступ). Целевая модель в банке — **GigaChat**: решение должно допускать замену модели без переписывания логики агента — LLM за слоем абстракции, промпты отделены от кода (соотносится с критерием «Инженерия» [§7.3](#sec-)).

Базовые рамки для всех команд: (1) в промпты передаются только синтетические данные хакатона — реальные клиентские данные не используются в принципе (датасет см. [§10.5](#sec-10-5)); (2) диалоги и артефакты не содержат ПДн/коммерческой тайны; (3) решение ведёт журнал действий агента (кто/что/когда — основа аудита, соответствует human-in-the-loop [§6.2](#sec-6-2)); (4) доступ по ролям — в MVP две роли (менеджер/модератор), передаются в заголовках `X-User`/`X-Role` ([§3](#sec-3)).

<a id="sec-10-9"></a>
### 10.9. Какие требования к креативам: брендбук, обязательные пометки, что проверять на 38-ФЗ?

Форматы MVP — два типа баннера (STORY, SMART_BANNER) и один тип контента (PROMO-экран). На выходе системы — **структурированный объект** (JSON по схемам [§2.6](#sec-2-6)–[§2.7](#sec-2-7)): рендеринг этих структур выполняет клиентское приложение. Для предпросмотра данных кампаний отрисовка контента может быть произвольная. Медиа можете для демонстрации брать свои; брендбук (шрифты, палитра, логотип) не предоставляется и не проверяется, AI-изображения людей не генерируются (генерация картинок — см. [§6.4](#sec-6-4)).

Маркировка рекламы по 38-ФЗ (ОРД, ЕРИР-токен, дисклеймеры, договоры) не входит в MVP, но можно реализовать как дополнительное требование (см. [§6.4](#sec-6-4)): ассистент не обязан её реализовывать. Требования ЦБ в MVP проверять не нужно.

<a id="sec-10-10"></a>
### 10.10. Какие метрики успеха самого продукта и что считается неудачей?

Критерии оценки решения — [§7](#sec-7) (функциональность, качество диалога, инженерия, UX превью, демо). Продуктовые метрики прототипа, которые рекомендуется показать на демо:

- **скорость**: бриф → собранная кампания за один диалог (эталон — [§9](#sec-9));
- **корректность автозаполнения**: доля полей/сущностей, принятых пользователем без правок;
- **валидность**: 0 ошибок JSON-схем к моменту отправки на модерацию; warnings либо устранены, либо объяснены;
- **восстановление после ошибок**: отклонение модератора → исправление → повторная отправка в том же диалоге.

Чего не должно быть на демо: ассистент додумывает и подставляет значения без вопроса (нарушение [§6.2](#sec-6-2)); генерирует JSON, не проходящий схемы; совершает пишущие действия без подтверждения; теряет контекст при многошаговом диалоге; не может объяснить пользователю статус кампании или причину ошибки валидации.
