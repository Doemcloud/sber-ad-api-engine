# База данных: Platform V Pangolin DB

Сервис кампаний хранит данные в **Platform V Pangolin DB** — СУБД СберТеха на основе PostgreSQL. Схема повторяет доменную модель ТЗ (§2). Приложение использует только стандартный SQL и протокол PostgreSQL, поэтому работает с Pangolin без изменений.

## Как запускается

- `docker compose up` поднимает сервис `db`. Образ задаётся переменной `PANGOLIN_IMAGE`. Pangolin распространяет СберТех по запросу ([pangolin.sbertech.ru](https://pangolin.sbertech.ru)), публичного образа нет. Поэтому по умолчанию стоит совместимый `postgres:16-alpine`: так прототип запускается на любой машине.
- API подключается по `DATABASE_URL` и при старте применяет схему: `api/internal/store/migrations/001_schema.sql`, скрипт идемпотентен. Если база пустая, API заполняет её моками заказчика из `data/mock/`.
- Если `DATABASE_URL` не задан (unit-тесты, быстрый запуск без СУБД), используется файл-снимок `STATE_FILE`.

Чтобы подключиться к Pangolin на стенде, укажите адрес его экземпляра:

```env
DATABASE_URL=postgres://user:password@pangolin-host:5432/adcamp?sslmode=require
```

## Схема (по ТЗ §2)

| Таблица | Сущность ТЗ | Содержимое |
| --- | --- | --- |
| `topic`, `tag`, `channel`, `banner_type`, `segment_type`, `segment`, `place` | справочники §2.9 | тематики; теги (можно создавать); каналы iOS/ANDROID/WEB; форматы STORY и SMART_BANNER с лимитами длины; сегменты с числом клиентов; места показа с форматом по умолчанию |
| `campaign` | CAMPAIGN §2.2 | шапка, период, тематика, тип аудитории, статус жизненного цикла, `published` |
| `campaign_tag`, `campaign_place` | теги, места показа (N:M) | |
| `campaign_segment` | аудитория §2.4 | сегменты включения и исключения (`kind`) |
| `banner` | BANNER §2.6 | JSON-контент баннера (`jsonb`) |
| `content` | CONTENT §2.7 | документ PROMO-экрана (`jsonb`) |
| `creative` | CREATIVE §2.8 | баннер + промо-экран + канал; уникален по паре «баннер — канал» |
| `lifecycle_transitions` | аудит §6.3 | все пишущие операции и переходы статусов: кто, когда, что изменил |
| `id_sequence` | — | следующие id по видам сущностей (кампании 1xx, баннеры 2xx и т. д., как в моках) |

Ограничения целостности заданы в самой БД:
- внешние ключи на справочники;
- `CHECK` для статусов, типа аудитории, формата времени `ЧЧ:ММ`, диапазона CTR;
- уникальность названия кампании;
- каскадное удаление дочерних сущностей вместе с кампанией.

Аудит хранится без внешнего ключа, поэтому история остаётся и после удаления кампании.

## Проверка

```bash
cd api && TEST_DATABASE_URL=postgres://user:pass@localhost:5432/adcamp_test?sslmode=disable go test ./internal/store/
```

Тест заполняет пустую базу из моков, меняет кампанию, перечитывает всё состояние из БД и сравнивает с исходным.
